# NYC Public Transportation Data Pipeline

**End-to-end ETL-проект для сбора, обработки и анализа данных об общественном транспорте Нью-Йорка.**

Проект реализует ETL Pipeline для данных о пассажиропотоке автобусного и метрополитенного транспорта Нью-Йорка. Данные извлекаются из открытых API, проходят валидацию, загружаются в PostgreSQL, обрабатываются с помощью SQL и используются для построения аналитических дашбордов в Apache Superset.

## Описание проекта

Цель проекта — разработать полноценный ETL Pipeline для сбора и анализа исторических данных о пассажиропотоке общественного транспорта Нью-Йорка.

Проект охватывает два направления:
- Автобусный транспорт (Bus).
- Метрополитен (Subway).

Основные задачи:

- Получение данных из публичных API.
- Пакетная обработка больших объёмов данных.
- Валидация и проверка качества данных.
- Загрузка данных в PostgreSQL.
- Организация многоуровневого хранения данных.
- Трансформация данных с помощью SQL.
- Подготовка аналитических таблиц.
- Визуализация результатов в Apache Superset.

## Источники данных

Используются два набора данных NYC Open Data.

### 1. Bus Hourly Ridership

[NYC Bus Hourly Ridership API](https://data.ny.gov/resource/gxb3-akrn.json)

Содержит почасовую информацию о пассажиропотоке автобусного транспорта.

Основные поля:
- Время поездки.
- Автобусный маршрут.
- Способ оплаты.
- Категория тарифа.
- Количество пассажиров.
- Количество пересадок.

### 2. Subway Hourly Ridership

[NYC Subway Hourly Ridership API](https://data.ny.gov/resource/5wq4-mkjj.json)

Содержит почасовую информацию о пассажиропотоке метрополитена.

Основные поля:
- Время поездки.
- Идентификатор станции.
- Название станции.
- Район Нью-Йорка (Borough).
- Способ оплаты.
- Категория тарифа.
- Количество пассажиров.
- Количество пересадок.
- Географические координаты.

**Период исторических данных:** 1–14 июня 2025 года.

## ETL Pipeline

### 1. Extract — извлечение данных

- Получение данных через NYC Open Data API.
- Пакетная загрузка записей.
- Использование offset-based pagination.
- Сохранение прогресса загрузки с помощью checkpoints.

### 2. Validate — проверка данных

Каждая полученная запись проходит проверку перед загрузкой.

Проверки включают:
- Наличие обязательных полей.
- Отсутствие недопустимых пустых значений.
- Корректность числовых показателей.
- Проверку целостности данных.

Некорректные записи отделяются от корректных и сохраняются для дальнейшего анализа.

### 3. Load — загрузка данных

Проверенные записи загружаются в PostgreSQL в схему RAW.

Для предотвращения дублирования используется механизм обработки конфликтов PostgreSQL (`ON CONFLICT`).

### 4. Transform — трансформация данных

Данные проходят через три уровня обработки:

- **RAW:** исходные проверенные записи.
- **STAGING:** очищенные и стандартизированные данные.
- **ANALYTICS:** аналитические таблицы, подготовленные для построения отчётов.

SQL-трансформации запускаются автоматически из Python после успешного завершения загрузки обоих источников.

### 5. Logging и Checkpoints

В проекте реализованы:
- Логирование выполнения ETL.
- Статистика обработки каждого batch.
- Обработка ошибок.
- Сохранение offset загрузки.
- Отслеживание статуса выполнения каждого источника.

Это позволяет отслеживать работу Pipeline и продолжать загрузку с последнего сохранённого checkpoint.

## Структура базы данных

База данных организована с использованием трёх схем.

| Схема | Назначение |
|---|---|
| `raw` | Хранение исходных проверенных данных |
| `staging` | Очищенные и стандартизированные данные |
| `analytics` | Аналитические таблицы для отчётности |

Основные аналитические таблицы:

- `analytics.fact_bus_hourly_ridership`
- `analytics.fact_subway_hourly_ridership`

Дополнительные таблицы, предусмотренные для дальнейшего расширения:

- `analytics.fact_bus_stop_ridership`
- `analytics.fact_subway_od_ridership`

## Аналитический дашборд

Для визуализации данных используется Apache Superset.

Создан дашборд **NYC Public Transportation Analytics**, включающий:

1. Total Bus Ridership — общее количество автобусных пассажирских поездок.
2. Total Subway Ridership — общее количество поездок на метро.
3. Bus Ridership Over Time — динамика автобусного пассажиропотока.
4. Subway Ridership Over Time — динамика пассажиропотока метро.
5. Top 10 Bus Routes by Ridership — десять наиболее загруженных автобусных маршрутов.
6. Subway Ridership by Borough — распределение пассажиропотока метро по районам Нью-Йорка.

## Установка и настройка

### Требования

- Python 3.13 или выше.
- PostgreSQL 16.
- Docker и Docker Compose.
- Git.

### 1. Клонирование репозитория

```bash
git clone YOUR_GITHUB_REPOSITORY_URL
cd Transport_New-York
```

### 2. Создание виртуального окружения

```bash
python -m venv .venv
source .venv/bin/activate
```

### 3. Установка зависимостей

```bash
pip install -r requirements.txt
pip install -e .
```

### 4. Настройка переменных окружения

В корне проекта необходимо создать файл `.env`:

```env
DB_HOST=localhost
DB_PORT=5432
DB_NAME=nyc_transport_analytics
DB_USER=your_username
DB_PASSWORD=your_password

SUPERSET_DB_PASSWORD=your_superset_db_password
SUPERSET_SECRET_KEY=your_secret_key
SUPERSET_ADMIN_PASSWORD=your_admin_password
```

Необходимо заменить примеры значений на собственные настройки.

**Важно:** файл `.env` содержит конфиденциальные данные и не должен попадать в GitHub.

### 5. Подготовка PostgreSQL

Необходимо создать базу данных PostgreSQL и подготовить необходимые схемы и таблицы.

Приложение подключается к PostgreSQL с использованием переменных окружения из `.env`.

### 6. Запуск ETL Pipeline

```bash
python -m nyc_transport_pipeline.pipeline
```

При запуске Pipeline автоматически выполняются:

1. Извлечение данных Bus и Subway.
2. Валидация полученных записей.
3. Загрузка корректных записей в RAW.
4. Трансформация RAW → STAGING.
5. Трансформация STAGING → ANALYTICS.

Прогресс извлечения данных сохраняется с помощью checkpoints.

### 7. Запуск Apache Superset

```bash
docker compose -f docker-compose.superset.yml up -d
```

После запуска Superset будет доступен по адресу:

```text
http://localhost:8088
```

Для входа используются учётные данные администратора, заданные в `.env`.

В Superset необходимо подключить аналитическую базу PostgreSQL и создать datasets на основе аналитических таблиц.
